# OMY contact physics: primary sources and experiment guidance

Research date: 2026-10-24. This is a source companion to the local bowl investigation, not a claim that a configuration has passed collection qualification. All external references below are NVIDIA documentation, upstream implementation documentation, or original research. Descriptions are paraphrases.

## Interpret the sources against the actual installation

The local environment has Isaac Lab 2.2.0, Isaac Sim 5.0.0.0, and bundled physics tensors `107.3.18+107.3.1`. Versioned Omni Physics 107.3 documentation is therefore a close match, but its online documentation includes features added after patch 107.3.18. Patch history matters even when the major/minor numbers match.

The collection's effective position-iteration cap was **16**, compared with the repository's normal scene cap of **32**. The robot requests 64, but that request is clamped by the scene. Describe the reduction as **32 to 16**, rather than 64 to 16.

The local asset audit and recording inspection found approximately 1 mm bowl walls, convex decomposition with an authored maximum of 256 hulls, friction coefficients of 2 on bowl and fingers, finger friction combine mode `max`, and CCD enabled on bowl and fingers. A hull limit is not a measurement of the number of cooked hulls. The recorded master gripper joint reaches its open position around row 103 while the object remains hooked. This prioritizes checking follower joints, actual collision shapes, and persistent contacts; it does not by itself distinguish penetration from a geometric hook.

**Joint-drive units change the interpretation substantially.** The authored USD angular drive stiffness is 100 and damping is 0.0002, in degree-based units. The live Isaac Lab values are stiffness **5729.578125 N m/rad**, damping **0.01145915594 N m s/rad**, and effort limit **16.5 N m**. The conversion factor is `180/pi`, approximately 57.2958. The stiffness therefore closely matches the problematic approximately 5700 example in NVIDIA's Robotiq guide; it is not a 100 N m/rad drive. These runtime values are recorded in [the CPU/32 diagnostic summary](../output/omy_diagnostics/20261024_bowl_contacts/cpu32/summary.json).

The preliminary CPU/32 diagnostic takes approximately 17–18.5 ms per control command without rendering/XR, but has substantial linkage error and unstable trajectories. This is evidence of performance headroom for further testing, not qualification of either its contact behavior or full XR throughput.

## Priorities suggested by the evidence

1. **Measure the failure directly.** Use per-contact separation, individual finger/follower states, target pose and velocity, and release behavior. Master-joint opening, task success, and mimic-joint error alone do not establish collision fidelity. Separate diagnostic runs from final timing runs.
2. **Test bounded gripper-drive tuning.** A useful controlled candidate is stiffness 275 in Isaac Lab's radian-based actuator configuration, master-joint speed approximately 2.93 rad/s, and the existing 16.5 N m effort cap. Derive damping from the actual effective inertia or test a documented range. The guide's example stiffness, damping, and torque are jointly derived for a particular model: 275 is an experimental starting point, not a validated universal setting. Check normal grasps, thin objects, lift retention, reopening, and release before adopting it.
3. **Inspect the cooked colliders.** Visualize the real bowl cavity/rim, fingertip shape, convex decomposition pieces, and actual contact locations. A thin rendered shell does not imply that the collision representation has that thickness. Prefer a small number of carefully fitted convex pieces when they preserve the grasp surfaces. Test geometry changes independently from solver changes.
4. **Retest friction on both contact materials.** With `max` combining and finger friction 2, lowering only bowl friction can leave effective friction at 2. Any material experiment must resolve both materials and their combine modes. High friction can sustain tangential resistance while a finger or collider remains loaded; it does not prove an adhesive mechanism. Lower-friction candidates also need a lift/slip check.
5. **Spend solver time where measurements justify it.** Compare 16/32/64 position caps with identical inputs. Benchmark CPU physics and 0/1/2/4 physics workers while preserving GPU rendering. If more accuracy is needed, compare 120 Hz/32 with 240 Hz/16 at unchanged action/render rates. Equal nominal iteration work does not imply equal cost or contact behavior.
6. **Treat newer solver ordering as an upgrade experiment.** `solveArticulationContactLast` first appears in 107.3.24, later than this installation. Authoring the attribute into USD does not prove the current binary implements it.

## Direct separation measurements

The tensor view needs a nonzero `max_contact_data_count` and a valid bowl-body filter. Each sensor/filter pair occupies only the slice given by `starts` and `counts`; unused buffer entries must not contribute to statistics. A separation below zero indicates overlap at that reported contact; `max(0, -separation)` gives depth in scene length units. This is a contact-based metric, not a complete volumetric intersection test: missed contacts or a finger already through a shell require collision visualization and trajectory checks too. Sources 12 and 20 explain the distance semantics and API.

```python
contact_view = sim_view.create_rigid_contact_view(
    finger_body_pattern,
    filter_patterns=[bowl_body_path],
    max_contact_data_count=4096,
)
forces, points, normals, separation, counts, starts = (
    contact_view.get_contact_data(physics_dt)
)
# For each sensor/filter pair, inspect only:
# separation[start : start + count]
```

Collect at each physics step rather than only at the 15 Hz action boundary. Report maximum and sustained penetration, contact identities, release delay, follower-joint errors, object pose/velocity, and successful lift/release across repeats. An alternative callback through `subscribe_contact_report_events` provides `ContactData.separation` and collider identities; attach `PhysxContactReportAPI` and use threshold zero for diagnostics. Source 21 documents buffer lifetime. Keep the diagnostic and timing configurations explicit so instrumentation overhead is not mistaken for solver cost.

For solver/performance comparisons, hold action sequence, initial state, rendering rate, control rate, recorder settings, device, and worker settings fixed except for the variable under test. A CPU/CUDA switch can change trajectories, so qualify behavior separately from throughput. A successful task predicate alone is insufficient when the object can be transported while hooked.

## Follow-up: mimic compliance and CPU/CUDA differences

The local mimic audit found four followers with natural frequency 1000 rad/s and damping ratio 0.05, and a right-outer follower configured with frequency 1e6 and zero damping ratio, treated as hard by the installed test formulation. A damping ratio of 0.05 is strongly underdamped. Source 26 recommends a ratio around or slightly above 1, with frequency chosen relative to timestep; at 120 Hz, its suggested initial product of 1 corresponds to about 120 rad/s. A controlled sweep of 120/300/1000 rad/s with ratio 1 or 1.2 is therefore justified. Track lag as well as oscillation and contact behavior. A hard-mimic comparison is useful diagnostically, but adding hard constraints can worsen the competition with drives and contacts.

Observed CPU linkage errors larger than CUDA errors are a local result, not proof of a documented CPU feature limitation. The SDK history includes backend-specific fixes, but the discovered later mimic/limit fix is specifically PGS/CPU, whereas this collector uses TGS. Do not diagnose this case as that known bug. The older fixed-root ordering fix was introduced alongside mimic compliance and is also not evidence of an outstanding installed-version defect. Prefer a minimized gripper/object reproduction with correct mass properties and controlled compliance before attributing the discrepancy to the engine. Sources 26 and 33 support this distinction.

## Follow-up: investigate unusually small Franka inertias

The authored asset audit reported kilogram-scale arm links with diagonal inertias often around 1e-6 kg m², including link 6 mass 1.12858 with diagonal `(2.605e-7, 3.990e-7, 4.705e-7)` and link 7 mass 0.40529 with diagonal `(6.317e-8, 6.320e-8, 1.061e-7)`, and COM at zero. Subsequent `body_properties` reads in [`cuda16_tuned_d06_contacts/summary.json`](../output/omy_diagnostics/20261024_bowl_contacts/cuda16_tuned_d06_contacts/summary.json) confirm the small runtime masses/inertia tensors. Composed transforms and a coherent physical reference must still be checked before calling this a particular unit-conversion error. The first-axis radii of gyration `sqrt(I/m)` are approximately 0.48 mm and 0.39 mm. For these arm links, that is a strong physical-plausibility concern rather than proof of a particular missing scale factor.

The vendor-hosted reference gives link 6 mass 1.666555 kg, COM `(0.060149, -0.014117, -0.010517)` m, and full tensor diagonal `(0.001964, 0.004354, 0.005433)` kg m², with nonzero off-diagonal entries. Link 7 has mass 0.735522 kg and tensor entries also on the 1e-3–1e-2 scale. These are an order-of-magnitude check on a **different mass-property set**, not direct replacements for the local diagonals. Source 27 explicitly states that its values are identification results, not official inertial properties. Source 28 supplies their research basis.

A reviewable correction path is:

1. Read runtime link mass, COM, and full inertia from the actual physics view, resolving link names/order. Record composed body transforms, `metersPerUnit`, `kilogramsPerUnit`, and `principalAxes` alongside authored attributes.
2. Compare inertia eigenvalues and radii of gyration against link dimensions and a consistent reference model. Check positive principal moments and triangle inequalities. Comparing one USD principal-axis entry to a URDF body-frame diagonal without rotation is insufficient.
3. For diagnosis, create an isolated override that preserves a known mass while recomputing COM/inertia from correctly scaled collision geometry. Explicit parent inertia overrides must be cleared/replaced as well; setting a density alone does not supersede them. Geometry-based inertia assumes a mass distribution and is not necessarily a hardware-accurate final model. Sources 14 and 29 describe authoring precedence and inference.
4. For a final asset repair, use one coherent mass/COM/full-inertia set from verified CAD, an identified Panda model with documented limitations, or a validated official simulator asset. Transform tensors and COM into each local body frame, diagonalize, author the principal-axis orientation, and avoid counting a fixed attachment twice. Sources 27–31 define the data and transformations.
5. Rerun free-motion tracking, static poses, contact grasp/release, and CPU/CUDA comparisons before retuning gains. Fixing inertia changes effective drive frequency and damping; gain values tuned against an invalid inertia can obscure the repair.

Increasing arbitrary armature or multiplying every inertia by a guessed common factor is a sensitivity experiment, not a physically established repair. Source 2 supports correcting mass/inertia conditioning and accounting for reflected rotor inertia when specifications justify it.
